# Internationalization (i18n) Delivery Standard

**Status:** normative · **Applies to:** WPMediaVerse Free + Pro (portable to every Wbcom plugin/theme) · **v1.0**

WPMediaVerse must be **translation-ready from day one**. Translations are generated externally (`wbcom-i18n-ai` reads `.wbcom-i18n.json`, scans `__()` calls → POT → per-locale `.mo` + `.json`; run `bin/i18n.sh` to compile). Our job is the **delivery plumbing**: every user-facing string must (a) have a PHP `__()` home so the scanner sees it, and (b) reach the surface that renders it through a path that actually applies the translation. A string that renders English on a fully-translated site is a delivery bug, not a translation gap.

This is the single source of truth for how every layer delivers strings. It exists because the recurring "frontend is not getting translated" reports all trace to one of the traps below.

---

## The one rule

> **Every user-facing string has a PHP `__()`/`_e()`/`esc_html__()` home, and every render path reads the translated value — never a hardcoded literal.** A literal is allowed ONLY as a JS fallback that mirrors an injected `__()` value. A literal that has no `__()` twin is invisible to the scanner and can never be translated.

---

## Delivery matrix — one row per render layer

| Layer | How a string is delivered | The rule you must not break |
|---|---|---|
| **PHP templates / classes** | `__()`, `esc_html_e()`, `_n()` with textdomain `wpmediaverse` (Free) / `wpmediaverse-pro` (Pro). Free auto-loads (wp.org); Pro registers its dir with `load_plugin_textdomain( 'wpmediaverse-pro', ... )` on `init` (EDD, not wp.org). | Never emit a user-facing literal without a translation function. Never resolve a label before `init` (WP 6.7 `_load_textdomain_just_in_time` notice). |
| **Interactivity Script Modules** (`src/blocks/*/view.js`, Pro gamification `*-store.js`, layout `*.js`) | Modules **cannot** use `wp_set_script_translations` (no per-module JED). PHP injects `wp_interactivity_state( 'mvs/<ns>' \| 'mvs-pro/<ns>', [ 'i18n' => [ ... ] ] )`; the store reads `state.i18n.<key>` with an English fallback. | **Every `state.i18n.<key>` a store reads MUST be a key in that namespace's injector.** A read-but-not-injected key silently renders the English fallback on all locales. |
| **Interactivity islands seeded per-instance** (media-upload, explore-feed render.php) | `render.php` calls `wp_interactivity_state()` (or passes `data-wp-context`) with a `'i18n'` map of `__()` values; the store reads `state.i18n.<key>`. | Every key the store reads MUST exist in that render.php's injected map. Keep the map and the store's reads in lockstep. |
| **Classic scripts** (`assets/js/frontend/mvs-rest.js`, `load-more.js`, Pro `connector-import.js`, `dashboard-connectors.js`, admin) | `wp_set_script_translations( <handle>, '<domain>', <dir>/languages )` makes `window.wp.i18n.__()` work, **and/or** `wp_localize_script( <handle>, <globalObj>, [ 'i18n' => [ ... ] ] )` with `__()` values. | If the JS reads `globalObj.i18n.<key>`, that key MUST be seeded in the PHP localize array. Ship the `.json` JED files for `wp.i18n.__()`. |
| **Messaging module** (`assets/js/messaging.js`) | A script module, so no JED. `print_messaging_config()` seeds `mvsMessagingConfig.i18n`; the store reads `config.i18n[str]`. | Never hardcode a user-facing default in the messaging store; every string comes from the config injector. |
| **Data sent to another user** (moderation, notifications) | Resolve the string in the recipient's locale on the **server**, not from the actor's JS. | Do not POST an actor-side English literal that becomes the recipient's notification. |

## Traps that caused real "not translated" bugs

1. **Read-but-not-injected key (dominant bug).** A store calls `state.i18n.viewMore` but the injector never defines `viewMore`. The state has no such key → the English fallback always wins. Fixed by adding the key to the injector; no JS change. *Audit:* diff every `state.i18n.<key>` a store reads against its namespace injector.
2. **Module `__()` (the WPMediaVerse regression this standard was written after).** A block `view.js` is a `viewScriptModule`; calling `window.wp.i18n.__()` inside it returns English on every locale because no JED is loaded for modules. Deliver via `wp_interactivity_state( ..., ['i18n'=>...] )` instead.
3. **JS-only literal.** A string that exists ONLY as a JS fallback (never in any PHP `__()`) is invisible to the POT scanner, so `wbcom-i18n-ai` never produces a translation for it. Every fallback literal must have a matching `__()` in the injector/localize array.
4. **Pro textdomain never loads.** Pro is EDD-distributed; WordPress only auto-loads catalogs from `wp-content/languages/plugins/`. Its own `languages/*.mo` load ONLY because `load_plugin_textdomain( 'wpmediaverse-pro', ... )` registers the dir — hooked on `init`, never earlier.
5. **Resolving labels before `init`.** `__()` before the textdomain loads returns English (and, on WP 6.7+, logs `_load_textdomain_just_in_time`). Resolve labels at render time, not on early hooks (e.g. quota-package names are stored raw and translated at display).

## Adding a new frontend string — checklist

- [ ] The string is wrapped in a PHP translation function somewhere (injector, localize array, or render.php `'i18n'` map), so the scanner sees it.
- [ ] If read by an **Interactivity store/module**: the key is added to the matching `wp_interactivity_state( 'mvs/<ns>' \| 'mvs-pro/<ns>', ['i18n'=>[...]] )` injector. The JS keeps the same English text as its `state.i18n?.<key> || 'English'` fallback.
- [ ] If read by a **classic script**: the handle has `wp_set_script_translations`, and any `globalObj.i18n.<key>` is seeded in `wp_localize_script`.
- [ ] `_n()` / placeholder (`%s`, `%d`) forms keep the whole phrase translatable (no string concatenation for word order).
- [ ] Adding a **new store namespace**? Add its injector call in the same commit — even with zero strings, so the path exists before the first string is added.
- [ ] Run `bin/i18n.sh` to regenerate `.pot` (+ `.mo`/`.json` when `.po` exist) so the new string enters the catalogs.

---

## How to verify delivery (per surface)

1. Install + activate a full locale: `wp language core install de_DE && wp site switch-language de_DE` (with a compiled `.mo`/`.json` present).
2. Load the surface and read the emitted state, not just the visible text:
   - Interactivity: parse `#wp-script-module-data-@wordpress/interactivity` → `state['mvs/<ns>'].i18n`. Every key the store reads must be present.
   - Classic: `window.wp.i18n.getLocaleData('wpmediaverse')` / `mvsMessagingConfig.i18n` etc.
3. A key **present with a translated value** = delivered + translated. A key **present with the English value** = delivered, awaiting a `.mo` regen (fine — plumbing is correct). A key **absent** = delivery bug; fix the injector.
4. Restore: `wp site switch-language en_US`.
5. After wrapping any previously JS-only literal, run `bin/i18n.sh` + regenerate translations so the new `__()` strings enter the POT/`.mo`.

## Reference implementation (v1.0)

**Free (`wpmediaverse`):**
- Interactivity injectors: `templates/partials/shared-ui-frame.php` (shared-ui), `includes/Core/TemplateHelpers.php::media_social_i18n_state()` (media-social, called from `media-single.php` + `album.php`), `templates/partials/dashboard-content.php` (dashboard), `src/blocks/media-upload/render.php` (media-upload), `src/blocks/explore-feed/render.php` (explore-feed).
- Classic localize: `wp_set_script_translations( 'mvs-rest', ... )` + `'mvs-load-more'` in `includes/Core/Plugin.php`.
- Messaging module: `print_messaging_config()` → `mvsMessagingConfig.i18n` in `includes/Core/Plugin.php`.

**Pro (`wpmediaverse-pro`):**
- Gamification store injectors: `templates/*-body.php` (battles/challenges/tournaments/streaks/compete/boosts) + `GamificationTemplateLoader`.
- Feed layout: `includes/Layouts/InstagramLayout.php::seed_i18n_state()`.
- Classic localize: `Plugin::connector_import_config()` (connector-import) + `wp_set_script_translations( 'mvs-dashboard-connectors', ... )`; `collection-picker` via `mvsProPicker.i18n`.
- Textdomain: `load_plugin_textdomain( 'wpmediaverse-pro', false, dirname( plugin_basename( MVS_PRO_FILE ) ) . '/languages' )` on `init` (`wpmediaverse-pro.php`).

**Pipeline:** `.wbcom-i18n.json` (config: domain, potFile, protect list, glossary, 10 locales) + `bin/i18n.sh` (make-pot → make-mo → make-json).
