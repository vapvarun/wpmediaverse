## Architecture rules (locked for 1.2.0 onward)

These are non-negotiable invariants checked in CI. Code that violates them fails the build. **No backward-compatibility shims, no `_deprecated_*` notices, no facades preserved for old call sites.** The plugin is new; we choose the right architecture and break old call sites loudly so they get fixed.

### Rule A — 100% REST API on the frontend. No `admin-ajax`.

Every frontend interaction (anything outside `wp-admin/`) goes through a REST controller under `mvs/v1`. No `wp_ajax_*` or `wp_ajax_nopriv_*` handlers may serve frontend traffic. No JS bundled for the public site may reference `admin-ajax.php` or `ajaxurl`.

**Why:**
- REST has nonces, rate limiting (`RateLimiter` middleware already in `includes/REST/`), schema validation, OpenAPI introspection. `admin-ajax` has none of those.
- Single auth model — REST cookie auth or application passwords; no two-paradigm support burden.
- `admin-ajax` blocks page rendering on shared-hosting setups where `WP_USE_THEMES` overhead serializes requests.
- Headless/decoupled deployments only need to expose `mvs/v1` — no admin-ajax compatibility surface to maintain.

**Current state:** ✅ already compliant on the frontend. Free has 3 admin-ajax handlers, all admin-only (`OverviewPage` demo data + welcome dismiss). Phase 6 migrates those to REST too — 1.2.0 ships 100% REST end-to-end.

**CI guard (added in Phase 1):**
```bash
# Fails if any frontend-loaded JS references admin-ajax
! grep -rln 'admin-ajax\|ajaxurl' assets/js/ src/blocks/ build/blocks/ \
  --exclude='*.min.*' --exclude-dir='admin' \
  | grep -v '^$'
```
Wired into the existing `wpcs` GitHub Action job and the local `bin/launch-readiness.sh` gate.

### Rule B — Composable units. No facades.

Every renderer, service, and block is a single-responsibility unit invokable in isolation. No "thin facade for backward compat" classes. No "main XService becomes a facade for the new collaborators." When a class grows beyond its responsibility, it splits into named services with no aggregator left behind.

The pattern: a service does one thing. Callers either inject the service they need (DI) or resolve it via the container (`Plugin::container()->get('key')`). Nothing wraps multiple services for the convenience of legacy call sites — there are no legacy call sites because we don't ship that.

**CI guard:** PHPCS sniff that fails on any class named `*Service` whose public methods proxy to ≥2 other `*Service` classes (facade detection). Reviewer rejects PRs proposing facades.

### Rule C — One calling surface per capability.

Each capability has one calling surface (a renderer / service / endpoint method) that powers all consumers. The same code path serves block render callbacks, shortcodes, REST endpoints, archive templates, and admin previews. No parallel implementations, no copy-paste between blocks and shortcodes.

The pattern: write `Renderer::render(array $args): string` once. Block render.php calls it; shortcode handler calls it; REST endpoint with `?html=true` calls it; legacy archive template calls it. Args are explicit; output is deterministic.

**CI guard:** code review (no static gate) — reviewer rejects PRs that add a second implementation of an existing render path.

## What's in 1.2.0

### Phase 1 — Free/Pro boundary interfaces *(blocks Pro restructure)*

Pro currently imports `WPMediaVerse\Repository\MediaRepository` and `WPMediaVerse\Core\TemplateHelpers` directly in 28 files. Free defines interfaces, registers them in the container, Pro switches to `Plugin::free_service()`. **No backward-compatibility for existing static call sites.**

- [ ] Create `includes/Repository/MediaRepositoryInterface.php` — extract every public method `MediaRepository` exposes today as interface methods.
- [ ] `MediaRepository` declares `implements MediaRepositoryInterface`.
- [ ] Create `includes/Core/TemplateHelpersInterface.php` — same pattern.
- [ ] Convert `Core\TemplateHelpers` from a static utility class to an instance class implementing `TemplateHelpersInterface`. **Static method signatures (`TemplateHelpers::media_thumbnail(...)`) stop working entirely.** No singleton, no pass-through. Callers (Free internal + Pro) resolve the instance via container.
- [ ] Register both in `Core\ServiceContainer` under keys `media_repository` (already there) and `template_helpers` (new).
- [ ] Sweep every Free-internal `TemplateHelpers::method()` call site, replace with container resolution. About 15 sites in templates and admin pages.
- [ ] PHPUnit: assert `Plugin::container()->get('media_repository')` and `get('template_helpers')` return objects implementing the new interfaces.
- [ ] All quality gates green: PHPCS + PHPStan + PHPUnit + Plugin Check.
- [ ] Add Rule A CI guard.

## Sequencing

```
Phase 1 (defines interfaces, blocks Pro Phase 1)
  ↓
Phase 2 + Phase 3 + Phase 4 + Phase 5 + Phase 7  (parallel — all independent)
  ↓
Phase 6 (admin admin-ajax → REST migration)
```

Phase 6 last because the admin REST endpoints can be added alongside other work, but the cutover (deleting the admin-ajax handlers + updating admin JS) is a single sweep that needs to land near the end of the cycle to avoid mid-stream merge conflicts on `OverviewPage.php`.
