## Architecture rules (locked for 1.2.0 onward)

These are non-negotiable invariants checked in CI. Code that violates them fails the build. **No backward-compatibility shims, no `_deprecated_*` notices, no facades preserved for old call sites.** The plugin is new; we choose the right architecture and break old call sites loudly so they get fixed.

### Rule A — 100% REST API on the frontend. No `admin-ajax`.

Every frontend interaction (anything outside `wp-admin/`) goes through a REST controller under `mvs/v1`. No `wp_ajax_*` or `wp_ajax_nopriv_*` handlers may serve frontend traffic. No JS bundled for the public site may reference `admin-ajax.php` or `ajaxurl`.

**Why:**
- REST has nonces, rate limiting (`RateLimiter` middleware already in `includes/REST/`), schema validation, OpenAPI introspection. `admin-ajax` has none of those.
- Single auth model — REST cookie auth or application passwords; no two-paradigm support burden.
- `admin-ajax` blocks page rendering on shared-hosting setups where `WP_USE_THEMES` overhead serializes requests.
- Headless/decoupled deployments only need to expose `mvs/v1` — no admin-ajax compatibility surface to maintain.

**Current state:** ✅ already compliant on the frontend. Free has 3 admin-ajax handlers, all admin-only (`OverviewPage` demo data + welcome dismiss). Phase 6 migrates those to REST too — 1.2.0 ships 100% REST end-to-end.

**CI guard (added in Phase 1):**
```bash
# Fails if any frontend-loaded JS references admin-ajax
! grep -rln 'admin-ajax\|ajaxurl' assets/js/ src/blocks/ build/blocks/ \
  --exclude='*.min.*' --exclude-dir='admin' \
  | grep -v '^$'
```
Wired into the existing `wpcs` GitHub Action job and the local `bin/launch-readiness.sh` gate.

### Rule B — Composable units. No facades.

Every renderer, service, and block is a single-responsibility unit invokable in isolation. No "thin facade for backward compat" classes. No "main XService becomes a facade for the new collaborators." When a class grows beyond its responsibility, it splits into named services with no aggregator left behind.

The pattern: a service does one thing. Callers either inject the service they need (DI) or resolve it via the container (`Plugin::container()->get('key')`). Nothing wraps multiple services for the convenience of legacy call sites — there are no legacy call sites because we don't ship that.

**CI guard:** PHPCS sniff that fails on any class named `*Service` whose public methods proxy to ≥2 other `*Service` classes (facade detection). Reviewer rejects PRs proposing facades.

### Rule C — One calling surface per capability.

Each capability has one calling surface (a renderer / service / endpoint method) that powers all consumers. The same code path serves block render callbacks, shortcodes, REST endpoints, archive templates, and admin previews. No parallel implementations, no copy-paste between blocks and shortcodes.

The pattern: write `Renderer::render(array $args): string` once. Block render.php calls it; shortcode handler calls it; REST endpoint with `?html=true` calls it; legacy archive template calls it. Args are explicit; output is deterministic.

**CI guard:** code review (no static gate) — reviewer rejects PRs that add a second implementation of an existing render path.

## What's in 1.2.0

### Phase 0 — URL signing consolidation + schema cleanup *(highest leverage; do first)*

> **Why this is Phase 0.** The 1.1.3 patch shipped a `Services/MediaUrl.php` static helper as a workaround for the fact that signing lives at the wrong layer (REST response filter `mvs_media_response`) and media references are stored as varchar URL columns instead of `mvs_media_index.id` foreign keys. Templates / BP integration / Pro feed-cards each had to remember to call `MediaUrl::for_file()` separately — the CI grep guard catches most leaks but not all (the lightbox URL leak slipped past it). The structural fix moves signing into the data layer (`MediaRepository::get`) and migrates URL columns to BIGINT FK columns referencing `mvs_media_index.id` (NOT WP attachment IDs — Migration v8 already dropped the WP `attachment_id` bridge from the index). Once this lands, `MediaUrl` is retired, the CI grep guard is retired, and every future caller is automatically safe.

#### 0a — Move always-sign into `MediaRepository::get`

- [x] `MediaRepository::get($id, 'file_url')` returns a signed URL by default for every caller (REST controllers, templates, BP integration, blocks).
- [x] `MediaRepository::get($id, 'thumb_large'|'thumb_medium'|'thumb_thumb')` returns signed URLs.
- [x] `MediaRepository::get($id, 'watermark_url')` returns signed URLs (closes the today-unsigned watermark leak vector).
- [x] New `MediaRepository::get_filesystem_path($id)` — returns absolute filesystem path. Internal callers that need to read the file directly (Whisper transcription, watermark generation, EXIF strip) use this; the URL never appears.
- [x] Delete `Core/Plugin::maybe_sign_file_url` — signing is now in the data layer.
- [x] Delete `Services/MediaUrl.php` — retired. 25 call sites switched to `MediaRepository::get`/`find_by_url`/`get_broadcast_url`.
- [x] Delete the `// CI: storage-internal` markers — internal callers use `get_filesystem_path` / `get_raw` instead. (`bin/ci-local.sh` exclusion still to remove when re-enabled.)
- [x] PHPUnit: integration tests on `MediaRepository::get` for every URL field — `file_url`, `thumb_large`/`medium`/`thumb`, `watermark_url`, plus contract tests for `get_raw`, `find_by_url`, `get_broadcast_url`, `get_filesystem_path`.
- [ ] Browser-verify: load `/media/`, BP activity stream, and lightbox on `mediaverse.local` — zero 403s, zero broken-image icons.

#### 0b — Schema migration: URL columns → media IDs (FK to `mvs_media_index.id`)

URL-storage is the root cause of the 1.1.3 signing patch cycles. Migrate to BIGINT FK columns referencing `mvs_media_index.id`; templates compose the URL on read via `MediaRepository::get`.

- [ ] Pro coordinates: `mvs_competitions.cover_image_url` (varchar 500) → `mvs_competitions.cover_media_id` (BIGINT(20) UNSIGNED, FK to `mvs_media_index.id`). **Note:** `mvs_media_index` is the source of truth for media (no WP attachments — Migration v8 dropped the WP `attachment_id` column from the index). Pro plan Phase 0 ships the column on Pro side; Free Phase 0 ships the migration utility.
- [ ] New `Core/Migrator::migrate_url_column_to_id($table, $url_col, $id_col)` — backfills the new column by parsing each URL via a new `MediaRepository::find_by_url($url)` reverse-lookup helper.
- [ ] Drop `cover_image_url` column once migration verified on a fresh Docker run + manual spot-check.
- [ ] No backward-compat: code that tries to write `cover_image_url` after the migration gets a fatal. Tagged Rule B (no facades) — we don't ship a "shadow column" for legacy callers.
- [ ] Repeat the same migration for any other discovered URL columns during Phase 0 audit (audit step is itself a checkbox).

#### 0c — E2E flow tests *(the gap that lightbox URL leak slipped through)*

Static analysis (PHPCS, PHPStan, regex CI guards) caught 90% of the 1.1.3 signing leaks but missed the lightbox bug because the URL was composed at render-time inside an Interactivity API store. Three Playwright E2E specs cover the silent-failure paths.

- [ ] `tests/e2e/upload-sign-serve.spec.ts` — upload media → grid render → click thumbnail → lightbox opens → image loads with HTTP 200 (NOT 403) → close. Asserts on the network panel response code.
- [ ] `tests/e2e/bp-activity-render.spec.ts` — post a BP activity with attached media → render activity stream → screenshot has loaded image (no broken-image icon, no `<img src="">`).
- [ ] `tests/e2e/challenge-cover-fallback.spec.ts` (Pro-paired) — create challenge with no cover → cards render the placeholder, never `<img src="">`. Asserts on `data-wp-class--mvs-card-cover-wrap--placeholder` evaluating true.
- [ ] CI gate — every PR runs the 3 specs against a fresh wp-env. Failure blocks merge.
- [ ] Document: this is the layer-2 verification that the grep CI guard explicitly cannot do — flow-tests catch what text-pattern matching misses.

**Acceptance for Phase 0:**
- `MediaUrl.php` deleted from `includes/Services/`.
- `Plugin::maybe_sign_file_url` deleted.
- No `// CI: storage-internal` markers in the codebase.
- Schema migration verified — Pro's `mvs_competitions.cover_image_url` column dropped.
- 3 E2E specs green in CI on a clean run.

### Phase 8 — BP activity content: structured storage replaces regex parsing

`Integrations/BuddyPress/ActivityContentIntegration::enhance_activity_media_content` parses saved BP activity HTML with regex to extract `<img>`, `<video>`, `<audio>` src and rebuild the markup. Fragile — every change to BP activity HTML risks a regression (4+ incidents in 1.1.x including the 1.1.3 URL-signing fix). The structural fix: store an `mvs_bp_activity_media` linkage row when MVS media is added to BP activity; render from the linkage table, not by re-parsing strings.

- [ ] New table `mvs_bp_activity_media`: `(id, activity_id BIGINT INDEX, media_id BIGINT, variant ENUM('image','video','audio','document'), position INT, created_at)`.
- [ ] On every `bp_activity_after_save` involving MVS media (detected via `mvs-activity-media-id` data attribute or upload context), write linkage rows.
- [ ] `ActivityContentIntegration::render` reads the linkage table and emits MVS markup via `TemplateHelpers::media_thumbnail()` — zero regex on saved HTML.
- [ ] One-time migration: `wp mvs migrate bp-activity-links` CLI backfills linkage rows from existing BP activity content (uses the legacy regex parser one last time, then never again).
- [ ] Keep regex parser as **deprecated fallback only** for activity rows that pre-date the linkage table AND have no backfill match. No new code path uses it.
- [ ] CI guard — no new code in `ActivityContentIntegration` may add a `preg_match` against `<img|<video|<audio` (regression detector).
- [ ] PHPUnit: integration test posts an MVS media via REST → asserts linkage row written → asserts render output uses signed URLs from `MediaRepository::get`.

## Sequencing

```
Phase 0 (URL signing + schema cleanup + E2E gate)  ← foundation; do first
  ↓
Phase 1 (defines interfaces, blocks Pro Phase 1)
  ↓
Phase 2 + Phase 3 + Phase 4 + Phase 5 + Phase 7 + Phase 8  (parallel — all independent)
  ↓
Phase 6 (admin admin-ajax → REST migration)
```

Phase 0 first because every later phase benefits — `MediaRepository::get` returns signed URLs by default, so the new code Phase 2/3/5/7/8 ships doesn't need a parallel `MediaUrl` path to remember. Phase 6 last because the admin REST endpoints can be added alongside other work, but the cutover (deleting the admin-ajax handlers + updating admin JS) is a single sweep that needs to land near the end of the cycle to avoid mid-stream merge conflicts on `OverviewPage.php`.
