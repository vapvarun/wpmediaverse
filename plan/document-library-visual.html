A document library that reuses the library you already have

Documents become one more media type, not a second content system. Folders get a single purpose-built table. The drive root is a number, not a row. What was a nine-table migration across fifty production sites is now one new table and five added columns.

01

What changed, and why it matters

The original design made documents a separate entity with their own tables. Reversing that removed every blocker in the audit rather than mitigating them.

The separation bought exactly one thing: a structural guarantee that a document could never appear in a media grid. It paid for that with two independent ID spaces — and the invoice was long.

Cost of two ID spacesUnder one
Nine Free tables need an object_type columngone
Four unique keys widened, two PRIMARY KEYs rebuilt on 50+ live sitesgone
Parallel comment scope, parallel taxonomy, parallel permission seamgone
New REST controllers for every social actiongone — /media/{id}/… already works
Quota system that cannot see documentsgone — resolves the owner already
PDF viewer rebuilt (it is keyed on media_id)gone — works untouched
The trade, stated plainly

“A document never renders in a media grid” becomes a query guarantee instead of a structural one. A missed filter puts a PDF in the explore grid — visible on sight, fixed in a patch. The alternative was a botched key migration during auto-update: silent, permanent, on every customer site. Trading an unrecoverable risk for a recoverable one is the right direction.

Three mechanisms hold the guarantee: one repository choke point, a one-pass audit of the ~66 files that query mvs_media_index directly, and a CI rule that fails any new query lacking a media_type predicate. That work ships before a single document row can exist.

02

The data model

Two relationships, both single-column and indexed. A document points at one folder; a folder points at one parent. No junction table, no meta join, no recursive query on any read path.

One migration trap

token_hash must be DEFAULT NULL. With DEFAULT '' every existing grant row takes the same value and ADD UNIQUE KEY fails on the duplicates. MySQL exempts NULL from UNIQUE — nullable is both correct and the only thing that works.

Why folders get a table, not a post type

wp_posts on a BuddyPress community holds 65 rows — 42 of them email templates, because community data lives in bp_* and mvs_* tables. At 10,000 members, folders would be ~99% of that table, and the three meta rows each folder needs would take wp_postmeta from 13 rows to tens of thousands, with a join on every listing.

A folder as a post also wastes 15 of 23 columns, including three empty longtexts. A term is worse still — wp_terms has no column for an owner, a timestamp or a status, and the folder view sorts by modified and shows owner.

And no folder-meta table. A folder’s twelve attributes are fixed and nearly all filtered or sorted on. That is the definition of a column.

The root is a number

folder_id = 0 on a document and parent_id = 0 on a folder both mean “at the drive root.” There is no root row — so no lazy creation, no ID cache, no delete guard, no race rule. Four mechanisms that existed only to represent an absence.

Folder rows scale with deliberate folder creation, not member count. Ten thousand members who never make a folder produce zero rows.

03

Three surfaces, not one tree

A folder shared with you lives in someone else’s drive — its parent chain ends at their root, not yours. Grafting it in would mean one item with two parents in two ownership domains.

My Drive
drive_type='user' · drive_id=me

What you own. Real folder rows, real hierarchy, root at 0.

Shared with me
computed from grants · KEY grantee_user

Entry points others gave you — not their drives. No row, no parent, nothing can be created in it.

Space drives
mvs_document_drive_owners filter

One per Space you are an active member of. BuddyNext answers; MediaVerse never reads bn_*.

Two details make the shared surface behave. Topmost-grant collapsing: granted both /Contracts and /Contracts/2026, you see one entry — otherwise the same files appear twice at different depths and people think they have duplicates. It is a path-prefix comparison in PHP over the grant set, no extra query.

Breadcrumbs are a leak vector

Open a shared folder and you are inside the owner’s tree. A full breadcrumb would show every ancestor name above your grant point — Clients / AcmeCorp-litigation / Contracts when you were given only Contracts. Folder names carry client identities and project codenames.

The breadcrumb starts at the highest ancestor you hold a grant on. Everything above renders as one non-navigable root crumb, never as names — in templates, in API payloads, everywhere.

05

Access — privacy is the default, grants are the override

This is where documents genuinely diverge from media, and the same column means something subtly different.

MediaDocuments
privacythe whole story — public media is browsable in Explorethe default answer absent a grant
Grantsrare — paid access rulesthe primary mechanism. This is a collaboration product
“Public” meansdiscoverable — feeds, grids, Explorereachable by URL, never discoverable
Defaultpublic (column default)private, set explicitly in the service

A member marking a contract public gets a URL anyone can open — they do not get it posted to the community feed. That is the safer reading of the word, and the one the UI must state.

Resolution ladder — two queries per page, at any page size

  1. Drive owner or adminSpace answer resolved once per request per drive and cached — never per row, or the membership lookup becomes the N+1 this exists to prevent.
  2. Explicit grantDocument grant first, then nearest folder ancestor. One query for the whole page.
  3. Privacy levelAncestor chain parsed from path — zero queries.
  4. DenyMost specific wins; highest permission among equals.
Found while checking team behaviour

Privacy is resolved at move time and written to the row — deliberately, so tightening a folder later cannot silently re-expose files. That blocks the dangerous direction and breaks the safe one:

A member drops ten public documents into /Working, realises the folder should be private, switches it — and the ten documents stay public. Nothing says so.

Fix: one indexed UPDATE over the subtree via path. Tightening cascades; loosening does not — an explicit private on a file outranks its container. With a confirmation, because it is a bulk permission change.

Never inferred, only named

Today get_media_type() ends return 'document' — anything unrecognised becomes a document, and the upload guard depends on that fallback to know what to reject. Both change together: return '', and reject on unknown.

Strictly safer than today. An unrecognised file is currently labelled a document then rejected by that label; afterwards it is rejected because it is unrecognised. The value 'document' is then produced by exactly one function, which returns a named type or null and has no default branch.

And grouping is by inclusion, never exclusion. The reference database already holds a row with an empty media_type. WHERE media_type != 'document' would sweep it into the media library; IN ('image','video','audio') never does.

Phase 1 ships before any document row exists. With one shared table the media-grid guarantee is a query guarantee — so the choke point, the audit and the CI rule land while there is still nothing to leak. Doing it afterwards means auditing under time pressure against live data.

Phase 0 is not optional. Who may grant access, and how a drive with no user owner is charged for storage, both change what the permission service and the upload path do. Deciding them after phase 3 means rewriting phase 3.

Nothing member-visible ships before phase 9. Phases 1–8 leave the feature reachable by API and admin only — the half-cooked state the three-entry-point rule forbids.

07

What needs deciding

Three calls before phase 3. All three are product decisions, not implementation details.

CallThe questionRecommendation
blocking
Who may grant		 Nothing says who can hand out access. The natural-looking choice — “edit implies share” — lets any editor mint an anonymous link to a contract. Drive owner and drive-admin only for v1. A fourth manage level fits the existing column later, and widening is additive.
blocking
Team-drive quota		 Quota is per-user throughout. A Space drive has no user owner — charge the uploader for storage they cannot clean up, or let it escape entirely? A drive-level allowance keyed on (drive_type, drive_id). Gates phase 11.
decide
Replace is permanent		 No version history is a settled decision. The mitigation covers accidental overwrite but not “the edit was wrong — give me yesterday’s file,” which is the case teams hit most. Keep the superseded file 30 days under a meta key, admin-restorable. Not versioning — an undo. Meta plus a cron sweep, no schema.
v1 scope
Anonymous links vs private community		 The REST gate 401s the whole namespace when private-community mode is armed — and BuddyNext arms it. Anonymous links would be dead on the only stated consumer. Disable anonymous links whenever the gate is armed, and say so in the UI, rather than punching a hole through it.
v1 scope
Rate limiting		 The limiter has zero call sites in Pro. Anonymous link redemption is an unauthenticated exact-match token lookup with no throttle. Not optional if anonymous links ship.
Separate cards — shipped bugs, found while planning

Album IDs collide with media IDs. Albums write their post ID into a column that auto-increments for media. On the reference install, row 77 is simultaneously an album with two items and an image with a real file path. Deleting that album destroys the image’s index row — the file survives on disk and vanishes from the library.

Categories carry two ID spaces. Album post IDs and media IDs both write to the same term-relationship column, so where the integers coincide each returns the other’s categories. Tags are clean.

Neither is caused by this feature and neither is fixed by it. Both need their own cards — bundling them into a feature release hides them.

08

Measured against Google Drive for a team

The storage model needs no changes to serve a team. The collaboration model needs five.

HoleWhat happensFix
data loss A departing member takes the team’s files Files belong to the uploader, and the deletion cascade purges a member’s media. Someone uploads 200 files to a Space drive, deletes their account, and the drive loses all 200. This is exactly why Google built Shared Drives. A branch in the cascade: purge personal-drive documents, reassign team-drive ones. No schema.
leak Tightening a folder doesn’t tighten its contents Make a folder private and the public documents inside stay public, silently. One indexed UPDATE over the subtree. Tightening cascades, loosening does not.
governance Who may share is undefined Whoever builds the endpoint invents the rule. Decide it — see above.
abuse Space drives have no ceiling The storage hole the spec itself rules out. Drive-level allowance.
designed Nothing showed what was shared with you A file shared from a private drive was unreachable if the notification was missed. Three virtual roots, topmost collapsing, truncated breadcrumbs. No schema.

Where this is already ahead of Drive

Duplicate detection on file hash — Drive happily stores the same contract nine times. A virus-scan seam the site owner wires to their own scanner. Metadata stripping, which Drive does not do at all: a .docx carries author names, tracked changes and deleted comments, and a shared contract leaking the other side’s internal notes is a real incident. And self-hosting — no third-party processor relationship, which for a team handling contracts is the entire reason not to use Drive.

Deliberate divergences

One folder per file. Google dropped multi-parenting too, but replaced it with shortcuts. Ours is a grant, which shares with a person, not a place. Acceptable for v1 and worth naming in the docs so it is not discovered as a bug.

Fewer preview formats. Drive previews about a hundred; we cover PDF natively, render markdown, text and CSV server-side, parse Word and Excel client-side, and show an honest metadata card for the rest. The rejection of Office Online and Google Docs viewers is deliberate — both require the file to be publicly reachable and ship customer documents to a third party, which destroys the permission model entirely. That divergence is a feature.
