It substituted curl (with real auth cookies) plus direct MySQL, which proves the server-rendered half honestly and proves nothing about client-side behaviour. freshness check and that the stale 2026-08-31 report would therefore have passed. **That was

## Findings

### F1 — Migrator v31 normalised a sentinel that was never wrong (fixed by reverting, PR #25)

Found by a **real two-file upload** through the dashboard — precisely what the curl half of this
walk structurally could not do. Both new rows landed on `drive_id = 0`, the state v31 had just
migrated away, because `PrivacyService::resolve_drive_for_user()` returns `array( 'user', 0 )` for
a personal drive deliberately. `UploadService:348`, `PrivacyService:453` and `MediaController:1037`
all branch on `drive_id <= 0`, four unit tests assert the tuple exactly, and
`PermissionService::drive_from_row()` already resolves `0` to `post_author`.

Both encodings are behaviourally identical:

    media 63322  stored user:0  ->  drive_of() user:1  can_share(author)=true
    media 63303  stored user:1  ->  drive_of() user:1  can_share(author)=true

The migration therefore rewrote valid data on every customer's media table for no gain, and could
never win against a writer that correctly emits the sentinel. Removed rather than compensated for,
2.4.0 being unreleased.

This also corrects the reviewer's earlier verdict on Basecamp 10259007636: that card's premise was
right, the encodings do differ. What was missed is that they are equivalent by design, so the
answer was "nothing to fix", not "migrate the data".

### Probe artefacts — investigated, NOT filed

Three candidates were defects in the probe, not the product. Recorded because this class of
mistake keeps recurring here:

- **Two cron hooks appear to fatal.** They do under `do_action( $hook )`, which appends `''` when
  called with no args, so a typed `int` parameter gets a string. Real cron uses
  `do_action_ref_array( $hook, [] )` (`wp-cron.php:191`) which passes nothing, letting
  `prune_events( int $days = 90 )` and `function ( int $after_media_id = 0 )` take their defaults.
  `wp cron event run mvs_story_cleanup` succeeds in 0.005s.
- **Private media appears to leak a servable URL to anon.** The probe matched `/uploads/` anywhere
  on the page, catching theme assets. Precise extraction found zero serve URLs and zero upload
  paths; the 403 page renders "This media is for members".
- **Four Pro admin pages 403 for an administrator.** All four were slugs invented from string
  constants, not registered pages — each returned an identical 2567-byte body. The real quota slug
  is `mvs-quotas` and it returns 200.

The 18-vs-19 grant count the worker flagged was also chased: 19 rows, 1 revoked, 18 active. Correct.
