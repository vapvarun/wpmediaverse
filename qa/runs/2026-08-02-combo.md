## Verified bugs (passed the gate)

### F1 — Every paginated Explore and profile page returns HTTP 404 while rendering correctly — Major — **FIXED, commit `95d5406f`**

**Cite:** runbook `C.anon.explore-feed` ("pagination that advances") and `C.anon.user-profile` ("pagination works at `/media/@<user>/page/2/`").

**Reproduced** (cookie-free client):

```
media/                          HTTP=200  cards=12
media/page/2/                   HTTP=404  cards=12
media/page/3/                   HTTP=404  cards=12
media/@oliver_brooks/           HTTP=200  cards=12
media/@oliver_brooks/page/2/    HTTP=404  cards=2     <- 14 items total, correct split
album/mountain-escapes/         HTTP=200  cards=6
collection/public-gallery/      HTTP=200  cards=60
```

Page 1 is 200 on every surface; **every page ≥ 2 is a 404 that renders the right content**. The profile page-2 response carries `<title>Oliver Brooks: Media – Page 2</title>`, the profile header, and the 2 remaining items, and has **no** `error404` body class. This is a soft-404, not a broken page.

**Why it matters:** the runbook calls the anonymous Explore feed "the acquisition surface". Search engines drop 404s from the index, so on this fixture only 12 of 60 public media are indexable; CDNs and reverse proxies typically refuse to cache 404s; uptime monitoring flags them. The content being correct is what makes it dangerous — nothing looks broken in a browser.

**Not core convention:** WordPress sets `is_404()` when the main query for a paged request finds no posts, but the plugin owns these routes, renders its own content through them, and the runbook promises pagination works. Setting the query up so core does not 404 (or asserting `status_header( 200 )`) is the plugin's contract to keep.

**Not in baseline:** absent from `FINDINGS-HISTORY.md` and all prior `qa/runs/*.md`.

**Root cause and fix (post-walk).** `WP::handle_404()` runs on the `wp` action and 404s any request whose main query found no posts. Our virtual routes have no posts by design, so every page past the first was 404ed before rendering.

`render_template()` already tried to heal this with `status_header( 200 )`, but it runs on `template_redirect` — long after `wp` — and its "never downgrade an explicit 4xx" guard could not tell core's incidental 404 from the members-only gate's deliberate 403, so it correctly refused to touch either and the heal never fired. Now prevented at source via `pre_handle_404`, scoped to the main query on our four query vars.

Re-verified: paginated pages 404 → 200 with identical content; non-existent media slug, non-existent profile, non-existent album and non-plugin pages **all still 404**; private and members-only media still return **403 + noindex** to anonymous visitors.

### F2 — Plugin templates emit a PHP deprecation on every render under a block theme — Major (from-origin) — **OPEN: attempted fix reverted**

**Cite:** the runbook's debug-log protocol: "`from` = our code emitted it. **Always a blocker.**" and "Silent warnings are the bugs that ship."

**Reproduced:**

```
load /media/tiny/  (plugin template)  -> debug.log grew 600 bytes
                                          1× "Theme without header.php ... deprecated"
                                          1× "Theme without footer.php ... deprecated"
load /           (theme-rendered)     -> debug.log grew 0 bytes
```

`templates/media-single.php` (lines 15, 17, 43, 719) and `templates/404.php` (line 25) call `get_header()` / `get_footer()`. Under a block theme — which has no `header.php` / `footer.php` — WordPress emits `_deprecated_file()` on each call.

**Why it matters:** Twenty Twenty-Four and Twenty Twenty-Five are block themes, so this is the WordPress default, not an edge case. Every single-media view on such a site writes two deprecation lines. On a busy site that is the debug log filled with plugin noise, and it is exactly the "silent warning" class the protocol exists to catch.

**Origin is ours, despite the file path.** The message points at `wp-includes/functions.php` because that is where `_deprecated_file()` lives; the *caller* is our template. The control test (home page → 0 bytes) isolates it to plugin-rendered pages.

**Not in baseline:** prior runs recorded only `for`-origin deprecations from other plugins (`wb-gamification`, `bp-verified-member`). This one is new and is ours.

**There is more to this than log noise.** On a block theme, `get_header()` currently renders **no site chrome at all** — measured on Twenty Twenty-Five, plugin pages had no site header, no navigation and no site title. That is very likely the same root cause as the support complaint that the single-media page "looks disconnected / feels like a random attachment page" (Basecamp #9962498757).

**Attempted fix, reverted — recorded so nobody repeats it.** Routing the templates through a helper that calls `block_header_area()` / `block_footer_area()` on block themes did restore the site header, navigation and title, and took the deprecation count to 0. But it **also stripped the document `<head>`**: those functions render only the header *template part*, they do not emit `<!DOCTYPE>`/`<html>`/`<head>` or call `wp_head()`, which `get_header()` does via theme-compat. The result was a fully unstyled page (0 stylesheets). Reverted in full, and re-verified back to 17 stylesheets with a proper `<head>`.

A correct fix has to emit the document shell itself and then the header part, which is a real design change to how plugin pages are rendered on block themes — not a call swap. It needs its own card.

### Two measurement traps hit during this walk

Recorded because both produced a *passing-looking* result that was meaningless:

1. **The first layout-matrix run was a no-op.** A shell loop with a spaced path silently failed, so `mvs_pro_feed_layout` was never set — all five "layouts" returned the same ~66 KB default page. Caught because five different layouts producing byte-identical output is not plausible. `wp option get` then showed the option did not exist at all. Redone through the MCP client, where the byte counts diverge as they should.

2. **The dashboard tabs are client-rendered**, so `curl | grep Battles` returns 0 whether the feature is on or off. The first degradation check "passed" against server HTML that never contains the tab in either state. Redone in the browser DOM, which shows the tab genuinely present when on and absent when off.
