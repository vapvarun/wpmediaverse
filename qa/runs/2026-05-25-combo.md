## Demoted (did not pass the gate)

### F-DRAFT-1 → CONFIRMED FN of F10/F11 (NOT a 1.4.0 regression)

**Original draft claim:** 5 shortcodes (`[mvs_album]`, `[mvs_lock_overlay]`, `[mvs_player]`, `[mvs_stats]`, `[mvs_upload]`) return 0 bytes with no args, violating `RENDER-STATE-RULES.md` §1.

**Gate verdict:** demoted to existing open finding.

**Reasoning (Q4 of the gate):** `qa/rules/RENDER-STATE-RULES.md` section 4 — "Current baseline (2026-04-23 scan)" — explicitly enumerates `build/blocks/media-player/render.php` (4 bare returns) and `build/blocks/lock-overlay/render.php` (2 bare returns) as the documented baseline at the time the rule was written. The rule's "Why this rule exists" line names F10 (`mvs/media-player` silent for images) and F11 (`mvs/lock-overlay` silent without mediaId) as the motivating incidents. **F10 and F11 are open findings in `qa/runs/FINDINGS-HISTORY.md`** with no CLEARED status, predating 1.4.0. They were knowingly accepted at 1.3.0 release.

**Net for this release:** none of the violations were introduced by 1.4.0 commits. The Option B refactor did not touch these render.php files. This is not a release blocker.

**New information surfaced by this walk:** the baseline scan only listed 2 files (media-player, lock-overlay). The current walk found 3 more (album-viewer, media-stats, media-upload) with the same shape. The 2026-04-23 baseline list under-counted — the next scan should expand it.

**Recommended follow-up (post-1.4.0 release):** open a single PR that adds `TemplateHelpers::render_block_empty_state()` calls to all 5 render.php files, then mark F10/F11 CLEARED. Track as a 1.5.0 line item, not a 1.4.0 blocker.
