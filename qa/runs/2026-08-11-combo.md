## Demoted (did not pass the gate)

- **F1 — activity composer 1-image preview is 64px, docs said 120-150px.** Re-verified: `assets/css/bp-integration.css` sets `width:64px; height:64px` with the comment *"fixed 64px square regardless of file count so the preview strip stays predictable; no grid-N-up variants needed."* A deliberate design, and it still satisfies the guard the row actually exists to enforce — *not a 200-320px hero*. **Docs corrected**, code untouched: `qa/inventory/WHAT-TO-CHECK.md` and two rows in `AGENT_SMOKE_RUNBOOK.md`.
- **F2 — streak-badge row named `TemplateHelpers::render_grid_item()` as a badge path.** Re-verified: `render_grid_item()` calls `get_display_name_plain()`, a different method from `get_display_name()`, and only the latter runs the `mvs_user_display_name` filter the badge is injected through. The exclusion is explicit and dated `@since 1.2.2` — badges are kept off grid thumbnails on purpose. The badge is present and correctly labelled everywhere it is meant to be. **Runbook row corrected** from 5 paths to 4, with the exclusion explained so future runs stop hunting for it.

### B — upgrade from 2.3.2 (3/0/0)

Database reset, WordPress reinstalled, then **Free 2.3.2 + Pro 2.3.2 installed from their GitHub release ZIPs**. Seeded three media rows (one `public`, one `private`, one `members`), two members, and — the row that matters — a **custom role `qa_community_member` created while the site was still on 2.3.2**, standing in for the BuddyPress / WooCommerce roles a real community's members actually hold. Confirmed it did *not* have `use_mvs_documents` at that point, because the capability did not exist yet. Then upgraded both plugins in place.

| Row | Result |
|---|---|
| B1 migration runs quietly, data survives | 2.3.2 → **2.4.0** both; `mvs_db_version` **25 → 27**; tables **32 → 34**; all **3 media rows preserved** with titles and privacy intact, including the private one; `mvs_caps_version` 2.3.2 → 2.4.0; **0 debug.log lines** |
| B2 migration is idempotent | two full deactivate/reactivate cycles — `db=27 tables=34 media=3 custom_role_cap=YES` both times, unchanged |
| B3 schema additions back-fill | `mvs_pro_folders` and `mvs_pro_document_search` were **created by the upgrade path**, not only by fresh activation — the document library is unusable without both, and `register_activation_hook` never fires on an update |

**The upgrade question this release exists to answer:** after upgrading, **every pre-existing role held `use_mvs_documents` — administrator, editor, author, contributor, subscriber, and `qa_community_member`** — and `user_can_use_documents()` returned YES for the member sitting on that custom role. No existing member loses their document library by updating. The new Explore Documents page was also created on upgrade, confirming `Activator::maybe_upgrade()` covers what the activation hook cannot.

Upgraded site serves: `/`, `/explore-media/`, `/my-media/`, `/upload-media/`, `/explore-document/`, `/my-media/documents/` all 200; unknown slug 404.
