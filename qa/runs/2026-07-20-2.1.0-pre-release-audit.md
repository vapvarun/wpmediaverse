## Root cause (unifies C1–C4)

2.1.0 introduces a new privacy policy — `Privacy\MemberDataMap` (erase vs **retain/anonymize**), executed by `Privacy\MemberPurger` and wired to the **formal GDPR eraser** (`GDPRService::register_erasers` → `wp_privacy_personal_data_erasers`). But the **self-service account deletion added this same release** (`AccountController::delete_account` → `AccountDeletionService::execute` → `wp_delete_user`) fires core's `deleted_user`, which is handled by the **pre-existing `Services\UserDeletionService` hard-delete cascade** (`UserDeletionService.php:26`). The two paths were never reconciled, and the new map's table/column coverage is incomplete.

## Critical

- **C1 (Free) — Self-delete destroys moderation evidence.** `UserDeletionService.php:103,127-135` hard-deletes `mvs_reports` by `reporter_id` AND `target_id` on `deleted_user`. `MemberDataMap` retain-map (170-175) says `mvs_reports` must be **retained/anonymized** ("a member must not erase the report another member filed about them"). `DELETE /mvs/v1/me` is **exempt from the suspension gate** (RestGate exempt list). ⇒ A reported/suspended member self-deletes and wipes the moderator's case. Defeats the release's own safety goal + Apple 1.2.
- **C2 (Free) — Erasure lies "done" while PII survives.** `mvs_conversations.created_by` (Migrator:432, `NOT NULL` user id) is on **neither** erase nor retain list (absent from `MemberDataMap`). The CI guard `bin/check-erasure.php` allowlist (34-47) has `creator_id` but **not** `created_by`, so it's blind. `GDPRService::erase_member` returns `done=true` (residue 0) while the erased user's id persists in every multi-participant conversation they created — violating `MemberPurger`'s own invariant ("'done' must be earned").
- **C3 (Pro) — GDPR erase breaks other members' battles.** `ProMemberData.php:77-80` puts `mvs_competition_entries` on the **erase (hard-delete)** list, while it anonymizes `mvs_competitions.winner_id` (retain, 108-117) on the explicit principle "erasing one participant must not destroy the event for everyone else." `BattleService::get_battle_data()` (971) and `hydrate_battle_row()` (777) `return null` if either entry is missing ⇒ surviving opponent's active battle 404s on accept/submit/vote/resolve **and vanishes from their list** — an invisible, uncancellable orphan.
- **C4 (Pro) — Same cause corrupts tournament brackets.** Deleted participant's entry ⇒ `format_player_from_entry()` renders `id=0` blank player in historical/active brackets other members are still in.

## Major

- **M5 (Free) — RestGate coverage guarantee is fictional.** `RestGate.php:41-42` claims a `RestGateCoverageTest` fails if a write route ships unclassified; **no such test exists** (only a hand-maintained ~24-route data provider in `RestGateTest.php`). A new between-member write silently defaults to `self` (no block gate) with zero test failure — the exact regression the subsystem was built to prevent.
- **M6 (Free) — Deleted actor orphaned in notifications.** `UserDeletionService` deletes `mvs_notifications` by recipient `user_id` only, never `actor_id`. `GDPRService::erase_social` (323) handles it but is **not wired** into `register_erasers` (only `erase_member` is). ⇒ "X liked your photo" survives with a dangling actor id.
- **M7 (Free) — Fail-open gate unmonitored.** `RestGate.php:310-323` intentionally passes writes through when targets don't resolve and fires `mvs_rest_gate_unresolved` "for the logs" — but nothing hooks it (or `mvs_rest_gate_denied`). Silent no-op in production; violates Coding Rule #8. (A journey even tells a human to grep for a log line no code writes.)
- **M8 (Pro) — Tournament bracket detail N+1 (public, unauth).** `TournamentService::get_bracket/format_match/format_player_from_entry` do `get_entry()` per player per match + uncached `get_userdata()`/`get_avatar_url()` per participant; `TournamentManager::render_detail` primes `cache_users()` for winners only. 64-bracket ≈ 190+ queries/load on a public endpoint. Violates the big-site N+1 rule.
- **M9 (Free) — MemberModeration admin UI breaks Rules #4 + #19.** `Admin/MemberModeration.php:194,197,229,231` inline hardcoded hex + inline-`style` + echoes raw HTML forms from a PHP class instead of `templates/admin/*.php`. (Notably would be flagged by `template-style-check.sh` — suggests local-CI wasn't run on these commits.)

## Resolution (2026-07-20, same day)

All 9 findings fixed + verified; verdict flips **BLOCKED → SHIP** pending the combo smoke.

- **C1/C2/M6** (Free `UserDeletionService` + `MemberDataMap` + `check-erasure.php`): account deletion now anonymises `mvs_reports` (reporter_id + target_type-scoped target_id) instead of deleting, erases notification `actor_id`, anonymises `mvs_conversations.created_by` on surviving threads; `mvs_conversations` added to the retain map and `created_by` to the gate allowlist (gate now classifies 25 tables). Commit `38524a3`.
- **C3/C4** (Pro `ProMemberData` + `TournamentService`): `mvs_competition_entries`/`_votes` moved erase→retain (anonymise), a `mvs_user_data_purged` listener covers Pro tables on account deletion, and read paths render a `user_id=0` entry as a "Unknown" ghost. Commit `e2892c6`.
- **Verified end-to-end** via `wp_delete_user`: reports/conversation rows survive with ids zeroed, actor notifications deleted, both battle entries present (opponent `user_id=0`), so the battle still resolves.
- **M5** RestGate coverage test (walks the live registry, 83 routes) + docblock corrected; **M7** fail-open gate logging wired to LoggerService; **M8** bracket N+1 batched (get_bracket 5 queries, get_participants 1); **M9** admin inline hex removed. Free `6d9974e`, Pro `e0c6e78`.
- Gates: `php -l`, WPCS (0 errors), PHPStan L5 (0 new) green both repos. Version bumped to 2.1.0 (all 8 values coherent) + 2.1.0 changelog written.

Remaining before tag: combo browser smoke + fresh green-pass JSON.
