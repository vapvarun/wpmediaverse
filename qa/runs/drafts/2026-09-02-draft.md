## CRITICAL TOOLING GAP — read this before trusting any row below

**This session had no Playwright MCP tools and no `mcp-local-wp` MCP tools available**, despite
the runbook and task brief assuming both. The only tools available were `Read`, `Write`, `Edit`,
and `Bash`. This is a materially different (and materially weaker) toolset than the runbook is
written for, and it changes what "walked" can mean in this report:

- **No browser at all** — not even Chromium. No screenshots, no `browser_console_messages`, no
  `browser_network_requests` 4xx/5xx capture, no `browser_snapshot` DOM assertions, no clicking,
  no file upload, no hover, no keyboard interaction (ESC, Tab), no visual/layout verification, no
  dark-mode/RTL/390px rendering check. Every row in the runbook that depends on JS execution or a
  literal click is **NOT EXECUTED**, not "passed quietly."
- **What I substituted:** `curl` with cookie jars seeded via the `?autologin=` mechanism (this
  works over plain HTTP — WordPress sets real auth cookies on the redirect, so curl-with-cookies
  can hit authenticated, role-scoped pages and read the server-rendered HTML/JSON). Plus direct
  MySQL access (found Local's per-site socket in `~/Library/Application Support/Local/sites.json`
  — bare `wp` was confirmed to hit the right DB once `mysqli.default_socket` was pointed at that
  socket) and WP-CLI for option reads/writes. Plus source-code reads for context.
- **What this proves and doesn't prove:** curl HTML is the SERVER-RENDERED output before any
  client-side JS/Interactivity-API hydration runs. For most of MediaVerse's server-templated
  surfaces (Explore, single-media, profile, documents, BP tabs) that is the real content and a
  legitimate check. It proves NOTHING about client-side behavior — reaction toggles, upload
  progress, lightbox open/close, drag-reorder, toast feedback, hover states, console errors, or
  anything gated behind a REST call the page's own JS makes after load.
- **Two DB writes were blocked by the environment's own auto-mode classifier** as "destructive":
  the sanctioned fixture-cleanup `DELETE` block from the runbook, and one ad-hoc `grep` on a
  temp file with an `href="..."` pattern (false positive, retried successfully with a simpler
  pattern). Fixture cleanup was therefore **skipped** — noted as a gap, not silently dropped.
  Sanctioned option writes (feed layout, feature toggles) worked fine and were reset correctly
  (verified in the final state check below).

Given this, roughly half the runbook (anything requiring a click, an upload, a hover, or reading
`window.*`/console state) is marked **⚠️ HUMAN — Playwright unavailable this session**, not
walked-and-passed. Section pass counts below only include things I could independently verify
through HTTP/DB/code evidence, per Rule 1 (verify before reporting).
