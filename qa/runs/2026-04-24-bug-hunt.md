### A1. Bogus `?mvs_tag=` shows full grid instead of empty state
**Severity:** Critical
**Category:** Empty-state / Silent fallthrough
**Surface:** `/media/?mvs_tag=thisdoesnotexist99999abc`
**What I did:** Navigated to `/media/` with a tag query param that matches no `mvs_tag` taxonomy term.
**What happened:** The page heading correctly says "Tag: thisdoesnotexist99999abc" but the grid below shows all 24 media items (full default explore feed). No empty state is shown.
**What should happen:** Per `RENDER-STATE-RULES.md` and `WHAT-TO-CHECK.md` §1: "no media tagged X" + clear-filter affordance. The tag filter is being silently ignored and the default query runs instead.
**Evidence:** Screenshot `ux-hunt-A1-bogus-tag-full-grid.png`. `document.querySelectorAll('.mvs-media-card').length` → 24.
**Root-cause hypothesis:** The explore template's tag filter branch does not validate whether the tag term exists before running the query. When the term yields 0 media, the query likely falls through to an unfiltered default instead of returning an empty set with messaging.

### Root cause (code level)

**File(s):** `templates/explore.php:55-67`, `templates/explore.php:296-304`, `templates/explore.php:470-527`

**Code flow:**
1. User hits `/media/?mvs_tag=thisdoesnotexist99999abc`.
2. `templates/explore.php:56-57` reads `$_GET['mvs_tag']` via sanitize_text_field and stores in `$mvs_filter_tag`.
3. Line 61-67 calls `get_term_by('slug', $mvs_filter_tag, 'mvs_tag')` for the heading — if it returns false, the raw input is used as the heading label (line 66). This is correct but purely cosmetic.
4. Lines 296-304 repeat the `get_term_by()` call for the query. If `$tag_term_obj` is false (term does not exist), the entire `if ( $tag_term_obj )` block is skipped — meaning `$mvs_tag_join` stays `''` and no `AND tr.term_taxonomy_id = %d` clause is appended to `$where`.
5. The query runs with zero tag constraints, returns all published/approved media, and `$has_items` is true.
6. The `else` branch at line 470 (the empty state) is never reached because `$has_items` is true.

**Fix direction (for the card):** At line 296, after `$tag_term_obj = get_term_by(...)`, add an early-exit gate: if `$mvs_filter_tag` is non-empty and `$tag_term_obj` is false, set `$has_items = false` and skip directly to the empty-state render with "Tag '{name}' not found. Browse all media" copy. Do not run the full query.

**Basecamp card fields:**
- Title: `Explore: bogus ?mvs_tag=xxx silently shows unfiltered grid with fake heading`
- Severity: Critical
- Files: `templates/explore.php:296-304`
- Reproduction: GET `/media/?mvs_tag=nosuchtag` logged in — heading reads "Tag: nosuchtag", grid shows full 24-item feed.
- Expected: empty-state naming the bogus tag + "Browse all media" CTA.

### A2. Album and Collection URLs documented as `/media/album/{id}/` and `/media/collection/{id}/` 404 — actual URLs are `/album/{slug}/` and `/collection/{slug}/`
**Severity:** Major
**Category:** URL routing / documentation mismatch
**Surface:** `/media/album/45/` (real existing album "Mountain Escapes"), `/media/collection/13/` (real existing collection "Nature Highlights")
**What I did:** Navigated to both documented URL patterns for albums and collections. Both album IDs confirmed published via `GET /wp-json/mvs/v1/albums/45` (returns `code: ok`, title "Mountain Escapes", 6 items). Same for collection.
**What happened:** Both return generic WP 404 ("Page Not Found"). The actual working URLs are `/album/mountain-escapes/` and `/collection/nature-highlights/` (slug-based, different CPT base slug).
**What should happen:** Per `MANUAL-UX-QA.md` §0 URL surface table, `/media/album/{id}/` and `/media/collection/{id}/` are listed as the canonical URLs. Either the rewrite rules are broken for the `/media/album/` prefix, or the docs are wrong.
**Evidence:** Screenshots `ux-hunt-A3-album-existing-404.png`. REST confirms album exists: `{"id":45,"title":"Mountain Escapes","link":"http://mediaverse.local/album/mountain-escapes/"}`. Visiting `/album/mountain-escapes/` works correctly (6 items, title, metadata).
**Root-cause hypothesis:** The plugin registered `mvs_album` CPT with `rewrite => ['slug' => 'album']` rather than `media/album`, or the rewrite rules for the `/media/album/{id}/` pattern were never registered (or need a flush). The `MANUAL-UX-QA.md` was written against a planned URL structure that wasn't implemented.

### Root cause (code level)

**File(s):** `includes/PostTypes/Album.php:45`, `includes/PostTypes/Collection.php:43`, `includes/Core/TemplateLoader.php:66-117`

**Code flow:**
1. `Album::register()` at line 45 sets `'rewrite' => ['slug' => 'album']` — WordPress therefore generates URLs as `/album/{post-slug}/`.
2. `Collection::register()` at line 43 sets `'rewrite' => ['slug' => 'collection']` — generates `/collection/{post-slug}/`.
3. `TemplateLoader::register_rewrite_rules()` (lines 66-117) registers only `/media/`, `/media/page/{n}/`, `/media/edit-profile/`, `/media/@{username}/`, and `/media/{slug}/` patterns. There is no `^media/album/...` or `^media/collection/...` rule anywhere in the file.
4. Hitting `/media/album/45/` matches the slug rule at line 113 (`^media/(?!.../)([a-z0-9][a-z0-9_-]*)/?$`) capturing `album` as the media slug — then `serve_single_media('album')` finds no media row for slug "album" and calls `set_404()`. The numeric `/45/` segment is simply dropped by the regex.
5. The documented `/media/album/{id}/` pattern was never implemented — the CPT was registered with a different rewrite slug than the docs specified.

**Fix direction (for the card):** Either (a) update `MANUAL-UX-QA.md` and `WHAT-TO-CHECK.md` to reflect the real URLs (`/album/{slug}/` and `/collection/{slug}/`), or (b) change `Album::register()` and `Collection::register()` rewrite slugs to `media/album` and `media/collection` and flush rewrite rules on update. Option (a) is a one-line doc fix; option (b) is a migration concern (existing permalink-stored links break).

**Basecamp card fields:**
- Title: `A2: /media/album/{id}/ and /media/collection/{id}/ 404 — CPT rewrite slugs don't match docs`
- Severity: Major
- Files: `includes/PostTypes/Album.php:45`, `includes/PostTypes/Collection.php:43`
- Reproduction: Visit `/media/album/45/` with a real album at ID 45 — 404. Visit `/album/mountain-escapes/` — 200.
- Expected: Either working `/media/album/` URLs or corrected documentation.

### A3. All page-level 404s (non-existent profiles, albums, collections, media) use generic WP 404 — not plugin-branded
**Severity:** Minor
**Category:** Empty-state / Branding
**Surface:** `/media/@nobody99999xyz/`, `/media/album/99999/`, `/media/collection/99999/`, `/media/9999999/`
**What I did:** Visited each URL pattern with IDs/usernames that don't exist.
**What happened:** All return a generic theme 404 page ("PAGE NOT FOUND — The page you were looking for doesn't exist. GO BACK"). No plugin-branded messaging, no "search for another user" or "browse explore" CTA.
**What should happen:** Per `WHAT-TO-CHECK.md` §1, single media 404 should be "plugin-branded 404", user profile should show "@user hasn't uploaded yet" (vs anon profile 404 separately).
**Evidence:** Screenshots `ux-hunt-A2-profile-nobody.png`. `document.querySelector('[class*="mvs"]')` returns `true` (plugin CSS loads), but the 404 content is entirely theme-controlled.
**Root-cause hypothesis:** The plugin does not intercept WP's 404 template for its own routes. A `template_include` or `404_template` filter targeting `mvs_*` query vars would allow branded 404s.

### Root cause (code level)

**File(s):** `includes/Core/TemplateLoader.php:218-231`, `includes/Core/TemplateLoader.php:279-286`

**Code flow:**
1. When media slug lookup fails, `serve_single_media()` at line 218-222 calls `$wp_query->set_404()` and `status_header(404)` and then returns — handing control back to WordPress's template hierarchy.
2. When a profile username lookup fails, `serve_user_profile()` at line 283-285 does the same.
3. WordPress's template hierarchy then resolves `404_template` — which loads the active theme's `404.php`. No `404_template` or `template_redirect` filter is registered anywhere in `TemplateLoader` or `Plugin.php` to intercept this and serve a plugin-branded template.
4. No `templates/404.php` or `templates/partials/404.php` exists in the plugin's template directory. The promise in `WHAT-TO-CHECK.md` §1 has no corresponding implementation.

**Fix direction (for the card):** Add a `404_template` filter in `TemplateLoader::init()` that checks `get_query_var('mvs_media_slug') || get_query_var('mvs_profile_user')`. If either is set, return a new plugin template `templates/404.php` that uses `get_header()`/`get_footer()` and renders a branded "not found" state with "Browse Explore" CTA instead of the theme 404.

**Basecamp card fields:**
- Title: `A3: Plugin-owned 404s (bad media slug, bad profile) serve theme 404 not plugin-branded template`
- Severity: Minor
- Files: `includes/Core/TemplateLoader.php:218-231` (single media), `:279-286` (profile)
- Reproduction: Visit `/media/@nobody_xyz/` — theme's generic 404 page renders.
- Expected: Plugin-branded "User not found. Browse Explore →" screen per WHAT-TO-CHECK §1.

### H1. PHP notices spam log: `as_has_scheduled_action()` called before Action Scheduler initialized
**Severity:** Major
**Category:** PHP log / Cron bootstrapping
**Surface:** Every page request — `debug.log`
**What I did:** Checked `wp-content/debug.log` after normal browsing session.
**What happened:** 2986 `PHP Notice: Function as_has_scheduled_action was called incorrectly` and `as_schedule_recurring_action was called incorrectly` messages, generated 2 per page load. Source confirmed: `wpmediaverse-pro/wpmediaverse-pro.php` calls these functions during plugin init, before Action Scheduler's data store is ready.
**What should happen:** Cron scheduling calls should be deferred to the `action_scheduler_init` hook or `init` hook (after AS is ready), not called during `plugins_loaded` / early init. This floods any production error log and makes real errors invisible.
**Evidence:** `grep -c "as_schedule_recurring" debug.log` → 2986. Source: `wpmediaverse-pro.php` lines calling `as_has_scheduled_action()` and `as_schedule_recurring_action()` without hooking into `action_scheduler_init`.
**Root-cause hypothesis:** Pro plugin schedules cron jobs in its early bootstrap (likely `plugins_loaded` or `mvs_loaded` callback) before WC Action Scheduler finishes initializing its data store. Should be wrapped in `add_action('action_scheduler_init', ...)`.

### Root cause (code level)

**File(s):** `wpmediaverse-pro/includes/Challenges/AutopilotService.php:68-79`, `wpmediaverse-pro/includes/Core/Plugin.php:82` (caller)

**Code flow:**
1. The free plugin fires `do_action('mvs_loaded')` during its `init` action at a standard priority (~10).
2. `wpmediaverse-pro.php` (line 204-219) hooks into `mvs_loaded` and calls `\WPMediaVersePro\Core\Plugin::init()` directly — this runs synchronously during `init`.
3. `Plugin::init()` at line 253-257 constructs `AutopilotService` and immediately calls `$autopilot_service->init()`.
4. `AutopilotService::init()` (line 68) calls `as_has_scheduled_action(self::AS_HOOK)` unconditionally — no deferral hook. Action Scheduler's data store initializes on `init@10`; `mvs_loaded` fires at the same or similar priority, so AS may not yet be ready, generating the "called incorrectly" notice.
5. Note: `CompetitionsScheduler::maybe_schedule_tick()` (line 43) and `StreakService::maybe_schedule_daily_cron()` (line 61) have already been fixed to defer to `init@20` — `AutopilotService::init()` was missed in that fix pass.

**Fix direction (for the card):** In `AutopilotService::init()`, move the `as_has_scheduled_action()` + `as_schedule_recurring_action()` calls (lines 68-79) into an `add_action('init', ..., 20)` callback — matching the pattern already used in `CompetitionsScheduler` and `StreakService`.

**Basecamp card fields:**
- Title: `H1 (Pro): AutopilotService::init() calls as_has_scheduled_action() before AS data store is ready — 2986 notices/session`
- Severity: Major
- Files: `wpmediaverse-pro/includes/Challenges/AutopilotService.php:68-79`
- Reproduction: Enable WP_DEBUG_LOG, load any page — debug.log fills with "Function as_has_scheduled_action was called incorrectly".
- Expected: AS scheduling deferred to `init@20` like CompetitionsScheduler and StreakService already do.

### Root cause (code level)

**Fix direction (for the card):** In `render_chat_panel()`, add an early return: `if ( get_query_var('mvs_messages_page') ) { return; }`. This suppresses the slide-out panel entirely when the dedicated full-page messages UI is active.

**Basecamp card fields:**

### B1. REST `?s=<script>alert(1)</script>` (pre-seeded) is a UX silent-fallthrough, not just security
**Severity:** Minor
**Category:** Input / Search / REST
**Surface:** `GET /wp-json/mvs/v1/media?s=%3Cscript%3Ealert(1)%3C/script%3E`
**What I did:** Sent the script-tag XSS payload to the media REST search endpoint.
**What happened:** Tags are stripped correctly (no XSS risk). The resulting empty string triggers the default query and returns 20 items — as if no search was performed. There's no `data.search_query` in the response showing what was searched. A client consuming this API has no way to know the search was sanitized to nothing.
**What should happen:** After sanitization, if the resulting search string is empty, the REST response should either (a) return 0 items with a `search_sanitized_empty: true` flag, or (b) treat empty-after-sanitization as "no results" rather than "no search". The current behavior is indistinguishable from a successful empty-search from the client's perspective.
**Evidence:** `?s=<script>` → 20 items. `?s=xyzzy_no_match` → 0 items. `?s=` → 20 items. `?s` absent → 20 items. Script tags silently produce the same result as omitting the search parameter.

### B2. "Complete your profile" dashboard banner does not dismiss and ignores Gravatar
**Severity:** Minor
**Category:** UX / Profile completeness
**Surface:** `/my-media/` (logged in as admin with Gravatar avatar)
**What I did:** Logged in as admin (who has a visible Gravatar in the profile card). Loaded `/my-media/`. Dismissed the banner (×). Reloaded the page.
**What happened:** The banner "Complete your profile. Add an avatar and bio to help others find you." shows every page load. The admin user has a Gravatar that renders in the profile card on the same page, yet the plugin treats the profile as incomplete. After dismissing (×), the banner reappears on reload — dismiss state is not persisted.
**What should happen:** (1) Gravatar should satisfy the "add an avatar" condition, or the copy should specify "upload a profile photo" vs generic "add an avatar". (2) Once dismissed, the banner should set a user meta flag and not reappear.
**Evidence:** Screenshot `ux-hunt-D2-my-media-dashboard.png`. Avatar visually present in profile card. Banner still showing. Cleared and reloaded — banner persists.
**Root-cause hypothesis:** The completeness check looks for a plugin-stored avatar meta key (`_mvs_avatar` or similar) not the WP-native `get_avatar()` / Gravatar. Dismiss state not saved to user meta.

### Root cause (code level)

**File(s):** `templates/partials/dashboard-content.php:28-36`, `templates/partials/dashboard-content.php:239-254`

**Code flow:**
1. Lines 28-36 call `$mvs_container->get('profile')->has_custom_avatar($mvs_current_user->ID)` — this checks for a plugin-stored avatar (custom upload via the avatar change flow in the edit form). Gravatar is served by `get_avatar_url()` (line 27) but `has_custom_avatar()` returns false for Gravatar-only users because Gravatar is not stored in plugin meta.
2. Line 239 evaluates `$mvs_profile_incomplete = !$mvs_has_custom || empty($mvs_current_user->description)`. Since `$mvs_has_custom` is false for a Gravatar user, the condition is always true regardless of Gravatar presence.
3. Lines 241-254 render the `<div class="mvs-profile-prompt">` banner with an inline `<script>` that reads `localStorage.getItem('mvs_profile_prompt_dismissed')`. Dismiss sets `localStorage.setItem('mvs_profile_prompt_dismissed', '1')` and hides the div via `style.display='none'`.
4. On the next page load PHP re-renders the banner HTML unconditionally (the `$mvs_profile_incomplete` check is always true for this user). The JavaScript then hides it again on the client — but there is a flash of the banner before JS runs, and in environments with JS disabled or slow connections the banner is permanently visible.
5. There is no server-side persistence of the dismiss state (no `update_user_meta` call, no nonce-protected AJAX endpoint).

**Fix direction (for the card):** Two separate fixes: (1) Change `$mvs_profile_incomplete` to also accept `get_avatar_url($id, ['default' => '404'])` returning a non-404 URL as satisfying the avatar condition (or update the copy to "upload a custom avatar"). (2) Persist dismiss to user meta: add a REST endpoint `POST /mvs/v1/profile/dismiss-prompt` that calls `update_user_meta($user_id, '_mvs_profile_prompt_dismissed', 1)`, and check `get_user_meta($id, '_mvs_profile_prompt_dismissed', true)` before rendering the banner PHP block.

**Basecamp card fields:**
- Title: `B2: Profile completion banner ignores Gravatar + localStorage-only dismiss reappears on every load`
